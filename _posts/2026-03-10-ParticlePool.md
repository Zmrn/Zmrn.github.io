{: .note}
> Unity的粒子系统（ParticleSystem）占用的内存很大，一个粒子系统会占用10KB左右的内存，哪怕是什么都没有修改的默认粒子也会占用9KB+。一些未加克制的项目中会使用大量的粒子系统，包含未显示的粒子在内，可能会有一万以上甚至数万个粒子系统，导致粒子系统占用的内存达到数百MB。在较低端的iOS系统上RAM非常宝贵，内存占用太多很容易导致app crash，所以对于有这种情况的项目来说，想办法节约粒子系统的内存十分有必要。
>
> 本文提供的粒子池实现仓库： https://gitee.com/Anso/unity-particle-pool

# 看看官方是怎么说的？

Unity官方也注意到了这个问题，并描述了一种可能的“建议”：

> **粒子系统池**
>
> 对粒子系统建池时，请注意它们至少消耗 3500 字节的内存。内存消耗根据粒子系统上激活的模块数量而增加。停用粒子系统时不会释放此内存；只有销毁粒子系统时才会释放。
>
> 从 Unity 5.3 开始，大多数粒子系统设置都可在运行时进行操作。对于必须汇集大量不同粒子效果的项目，将粒子系统的配置参数提取到数据载体类或结构中可能更有效。
>
> 需要某种粒子效果时，“通用”粒子效果池即可提供必需的粒子效果对象。然后，可将配置数据应用于对象以实现期望的图形效果。
>
> 这种方案比尝试汇集给定场景中使用的粒子系统的所有可能变体和配置会更具内存使用效率，但需要大量的工程努力才能实现。

官方给出的方案就只有这几行描述，距离具体实现还差得多。搜索可以发现已经有人按照这个思路初步实现了一个版本：

[https://github.com/CoolOverflow/UnityParticleSystemMemoryOptimization](https://github.com/CoolOverflow/UnityParticleSystemMemoryOptimization)

这个仓库里实现了基本的粒子池功能，将粒子参数记录在一个结构体中。这个结构体实际运行中占用内存约4KB+，相比原本的尺寸已经低了很多了。不过该项目完成度不高，使用起来还是颇为不便，也遗留了许多问题。本文基于这个思路，提供一个更加完善的，实际使用起来更为方便的实现。

# 我们想要一个什么样的粒子池？

## 池化粒子降低内存占用

将原本的粒子在Disable的时候移动到池子里，Enable的时候重新附加回来。通过这种方式大幅降低同时存在的粒子数量来降低内存消耗。

这需要在原本的粒子系统游戏对象上挂载一个Dummy组件，来监听游戏对象的Enable/Disable。上面提到的开源仓库就是这么做的。

本文的方案是，在运行游戏中实例化游戏对象时，删除游戏对象上的**ParticleSystem**（和**ParticleSystemRenderer**），将被删除的粒子系统的数据记录下来。当这个游戏对象Enable时，从粒子池中获取一个仅挂载了粒子系统的游戏对象（这里称之为**裸粒子**），将这个游戏对象作为原本游戏对象的子物体。

粒子池可以在加载游戏时预加载几十甚至数百个裸粒子以供使用。除非同屏显示的粒子数量超过预加载的数量，否则游戏中不需要派生新的裸粒子。

## 记录粒子参数

由于从粒子池冲拿回的粒子参数可能和最初的不一样，所以需要记录一下粒子的参数，在拿到裸粒子后将参数赋值给它。这需要让Dummy组件记录粒子的原始参数信息。

有很多粒子系统的参数可能是一样的，例如同一种子弹发射了数十发，会有至少数十个粒子使用的是同一套参数。为了节约内存，我们希望这些粒子可以使用同一份参数。

当我们对一个游戏对象应用粒子池时，先通过FNV算法计算粒子系统的所有参数得到一个哈希值，用粒子参数管理器哈希表里保存粒子的参数，即可做到同类粒子共享同一份数据。记录参数的时候，Dummy组件需要先计算并记录粒子的哈希值，如果发现这个哈希值是新值，才将粒子参数保存到管理器的哈希表里。使用哈希算法可能出现哈希碰撞，不过概率极低，实际使用中还没有遇到过这种情况。而且这种问题如果发生会非常明显，让特效负责人稍微修改一下粒子参数中的小数位即可改变哈希值规避碰撞。

值得注意的是，Dummy是成可以被派生（Instantiate）的。也就是说，以一个已经应用了粒子池的游戏对象（已经删除了原本的粒子系统，并记录了粒子数据哈希值的游戏对象）作为母本进行派生，派生出的对象也应是可用的。由于我们的Dummy实际上只记录了一个参数的哈希值和少数其他的几个变量，这是很容易做到的。基于此，如果有频繁发射子弹之类的需求，可以将一个已经应用过粒子池，并Disable的子弹作为母本来进行派生。这样可以防止每次创建新的子弹都要重新应用一次粒子池。

## 尽量减少特效负责人在开发中的负担

新增的工具不应降低开发效率，我们希望特效负责人在制作特效的时候能够一如既往，不要增加额外的工作。所以大多数工作需要在运行中进行。有两种方式：

1. 在非运行时，我们可以通过手动给预制件根物体附加一个标记组件，来时期在运行时自动执行记录参数和删除粒子系统的工作。这要求我们对所有需要应用粒子池的预制件手动附加组件。

2. 在游戏中如对象池之类的固定用于派生预制件的接口中统一挂载粒子池标记组件并运行，这样就不需要手动修改预制件。不过这要求游戏本身对对象派生功能有比较统一的一个或数个接口，改造起来可能需要一定的时间。

# 需要注意的问题

进行粒子池的开发前，有几个问题需要注意：

## 看不见的 ParticleSystemRenderer

当你给一个GameObject附加**ParticleSystem**时，Unity会同时给这个GameObject附加一个**ParticleSystemRenderer**组件。**ParticleSystemRenderer**也会占用一定的内存。这个组件在Inspector里是不可见的，哪怕打开Debug模式也看不到，所以很容易被忽视。**ParticleSystemRenderer**的参数可以直接在**ParticleSystem**的Renderer栏位进行配置，所以平时即使隐藏掉也不会有什么问题。但是如果在删除粒子的时候只调用了**Destroy(ParticleSystem)**，那么 **ParticleSystemRenderer** 是不会被删除的。

虽然**ParticleSystemRenderer**是不可见的，但是通过GetComponent还是可以获取到的，也可以通过**Destroy**进行删除。

```csharp
this.gameObject.AddComponent<ParticleSystem>();
// 给游戏对象附加粒子系统后，立刻就可以获取到ParticleSystemRenderer
var particleSystemRenderer = this.gameObject.GetComponent<ParticleSystemRenderer>();
```
## 无法直接池化Component

Component依附于GameObject，我们无法直接池化Component，只能池化GameObject。如果每次Enable的时候添加粒子系统，Disable的时候删除粒子系统，那样性能消耗会非常的高。

## 无法在Enable和Disbale时SetParent

在游戏对象Enable时给自己挂载一个子物体是做不到的，Unity不允许你这么做。

```csharp
public class ParticleSystemDummy : MonoBehaviour
{
    ... // 其它代码
    
    public void OnEnable()
    {
        // 获取池中的裸粒子
        var particleNode = ParticleSystemPool.Instance.Get();
        // 这是不行的！
        particleNode.SetParent(this.transform);
        
        ... // 其它代码
    }
    
    ... // 其它代码
}
```

这会导致Unity报出一个错误：

> <span style="color: red;">Cannot set the parent of the GameObject 'NakedParticle' while activating or deactivating the parent GameObject.</span>

不过，在Enable时给自己子物体挂载一个子物体是没问题的。也就是说我们要增加一层缓冲层游戏对象用于存放实际播放的粒子。

## 注意粒子系统间的引用关系

粒子系统可以通过子发射器（Sub Emitters）引用其他粒子系统。由于原本的粒子会在初始化的时候被删除，这部分的引用关系需要单独处理。可以在记录粒子数据时，将引用关系记录在Dummy中。虽然理论上可行，由于我在实际需求中并没有遇到很多这样的情况，所以没有进行支持。想要支持也并不困难。

## 勾选了Prewarm的粒子启动耗时很久

即使不进行池化，勾选了Prewarm的粒子在Enable的时候也会非常耗时。这本身就是一个只有在真正需要的时候才会勾选的高消耗选项。粒子池不能支持池化这样的粒子，否则会出现严重的性能问题。不过大多数情况下，这个选项都是不需要勾选的。

## 注意粒子的scalingMode

如果粒子的scalingMode为Local的话，其缩放只会应用裸粒子本身的缩放，与父物体无关。所以在记录粒子数据的时候，还需要记录Transform中的缩放数据，在scalingMode为Local时，需要应用这个数据。

{: .note}
> 理论上simulationSpace参数设置为World时也需要特殊处理，但我这边没有这种粒子，所以这里没有进行处理。需要处理的话将position之类的位置也进行记录即可。

## 注意直接引用粒子的情况

对于Animator直接控制粒子上的参数的情况需要多加注意。由于实际运行中，原本的粒子在记录完数据后已经被删除了，Animator将无法正常控制粒子的参数。可以考虑新增一个Agent对象将需要操控的粒子参数暴露出来，把Agent挂在粒子系统的游戏对象上，在Animator中控制Agent对象上的参数作为替代，由Agent代理操作粒子参数。由于我这边并没有很多这样的需求，所以选择直接不对这样的粒子进行池化。

其他地方也偶尔会有需要直接引用粒子的情况，这种情况需要基于粒子池进行专门的改造。不同项目的处理方式不同，无法统一，只能具体问题具体分析。

## 应用粒子系统的耗时

记录粒子系统通常可以在预加载之类的场景进行，对性能要求相对没有那么严苛。但是游戏中的粒子系统随时都有可能Enable/Disable，所以将记录的粒子参数应用到裸粒子上的性能消耗值得关注。

由于一帧Enable的粒子数量不同，粒子参数复杂度不同，应用粒子的耗时会有很多变化。

对于本文的实现，在实际项目的测试中得出了一些经验数据。测试中每帧同时Enable的粒子偶尔可能达到100个，多数情况是几十个。这已经不少了。

一些低端安卓设备上，应用数量较多的粒子偶尔会需要数毫秒的耗时。虽然大多数时候消耗都在1ms以下，但是偶尔的耗时增加依旧是值得关注的，可能会影响帧率。中高端设备基本都可以在1ms以下。

对于iOS系统，哪怕是一些比较旧的设备也基本可以稳定在1ms以下。iOS往往是内存导致闪退的重灾区，对性能有担忧又想要优化内存的话，可以考虑仅在编辑器和内存较少的iOS系统中启用该功能来节约内存。

### 通过【共享节点链表】实现的LRU数据结构来降低裸粒子的取用代价

从粒子池中获取裸粒子时，这个裸粒子可能已经被使用过一次了。如果取用的裸粒子上的参数恰好是我们需要的，那就不需要再耗时去应用这些参数了。这种情况实际上十分常见，特别是当池子足够大，或部分特效在短时间内反复播放的时候。对于这种情况，我们可以直接把粒子放到原对象下进行重播，不再需要专门设置粒子的参数。如果实际使用中可以优先取用粒子池中我们需要的粒子的话，可以节约很多应用粒子参数的耗时。
