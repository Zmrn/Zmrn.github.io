如何优雅地传递服务器数据变化？

分类: architecture

当服务器同步了一些数据变化到客户端的时候，在客户端的一种常见的做法是：将返回值的数据结构中的每一个字段读取出来，将需要的字段赋值给客户端相应的数据。这种做法没有什么问题，只是需要人来手动接入每个接口的字段，做这样的工作的时候，人偶尔还会犯些小错。

一种更好的做法是，保证服务器和客户端的数据结构和字段名完全一致。这样我们就可以通过一些自动化的手段将服务器发送过来的数据同步到客户端，并且完全不需要人参与。使得大部分服务器接口都不需要特别处理返回值。

我们设计一种叫做 Modifier 的数据结构，用来表达“数据的变化”。服务端完成业务逻辑的过程中，将数据库的所有变动记录在 Modifier 里，最后将 Modifier 发送到客户端。客户端接收这些变化，程序根据 Modifier 自动更新本地状态，再发送事件让界面和其他模块更新表现。

服务端的每一个数据库都可以认为是一个哈希表，由一个 key 索引到一个对象。如 units 数据库里维护着大量 unit 对象。为了能够使用 Modifier 自动同步数据，客户端也需要完全一致的数据结构。

当然，这里的“完全一致”指的是需要同步的数据完全一致，服务器可以有额外的不需要同步给客户端的私有数据，但只要某项状态通过 Modifier 传递，它在客户端镜像中就必须有相同的数据结构和字段。通常来说，只要是不涉及隐私或安全的数据，全都同步过来也没什么问题。

{
  "modifier": [
    {
      "type": "UPDATE",
      "target": "units",
      "id": "unit-1042",
      "path": "level",
      "value": 18
    }
  ]
}

Modifier 携带了“操作类型、目标对象、数据路径和最终值”。

下面使用完全虚构的单位数据说明 Modifier 的不同表达方式。无论修改字段、替换对象还是增删集合成员，传递的都是服务端确认后的最终结果。

更新对象字段

一次调用可以返回一个 Modifier 的列表，例如：把一个单位的多个字段变化拆成三条 UPDATE。每条变化都通过 target 和 id 定位对象，再由 path 指向一个属性，value 携带该属性的最终值。

这种方式只传递实际变化的字段，适合对象较大、单次变化较少的场景。

更新整个对象

亦或是，只发送一条 UPDATE ，但 value 直接携带完整单位；客户端收到后，以整个对象更新本地镜像。

根据情况可以采用不同方式。这种情况 path 可以不用传递，因为 target 就足以定位数据了。

新增与删除

ADD 和 REMOVE 改变的是单位集合本身。

ADD 携带新对象的完整值。服务器数据库添加了 unit-2048，客户端应用 Modifier 后，将同一个键和值加入本地数据库。

REMOVE 可以从数据库中删除特定对象。

通过这些操作，Modifier 可以完整表达服务器的数据变化，客户端只需要在接收到网络消息后解析 Modifier 即可自动完成数据更新。实际开发中可以提供很多便利，很多接口都可以“调后不理”。

服务端如何产生 Modifier

服务器侧的关键做法，不是在请求结束后扫描整份数据寻找差异，而是在业务修改权威状态时，就通过统一的更新层登记变化。同一份变化记录同时服务于三件事：更新服务器内存中的状态、组织需要持久化的写入，以及生成返回客户端的 Modifier。

Modifier 只表达状态最终发生了什么变化，不负责解释服务端如何计算出这个结果。对客户端而言，变化来自哪个内部流程并不重要。只要 Modifier 能完整表达最终状态，本地就可以用一致的方式处理。

同一次操作产生的多项变化，应当保证其 Modifier 列表的顺序，这样才能确保数据的正确性。如果服务器的一次操作中将一个对象先删除，然后又追加了回来，那么顺序反过来会发生严重的不同步问题。
